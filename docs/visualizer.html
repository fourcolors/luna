⑨ SDK Interaction — how Effect talks to the Claude Agent SDK

The bridge lives in packages/adapter-sdk. Two files: sdk-client.ts (the swappable seam) and adapter.ts (484 lines of Effect that owns 8 invariants).

Key insight: the SDK's query() returns a Query that is BOTH an async-iterable (messages flow out) AND a control handle (interrupt(), setModel(), setPermissionMode(), supplyToolPermissionResponse()). The adapter stashes it in a Ref so anyone in the session scope can drive the live subprocess without restarting it.

Two-layer split — why?

SDKClient (70 lines)
A 1-method service: query(params) → Query. Default uses real @anthropic-ai/claude-agent-sdk. SDKClient.fake(build) returns whatever Query stub you hand it — chat-service tests pass with zero network and no OAuth token.
SDKAdapter (484 lines)
All Effect-flavored work on top of the seam: AbortController, broker token rotation, env overlay, options merge, Stream bridging, idle timer race, hooks dispatch, Ref-based handle retention. This is where the invariants live.

Subprocess lifetime — one per thread, not per query

The SDK lazily spawns its bun subprocess on the first query() call. User messages stream in over stdin (the AsyncIterable<SDKUserMessage>); SDK responses come back as the Query's async-iterable face. The subprocess stays alive for the entire thread — that's why ChatService forces disableIdleTimeout: true. The thread Scope's AbortController is the ONLY thing that kills it. When you close a thread in the UI: scope closes → finalizer fires → abortController.abort() → SDK receives the signal → subprocess exits cleanly.
