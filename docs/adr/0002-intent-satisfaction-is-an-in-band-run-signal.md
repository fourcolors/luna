# 0002: Intent satisfaction is an in-band run signal, not a declared predicate

Status: Accepted

## Context

ADR 0001 established that job health means outcome freshness rather than exit success, and shipped a declarative `payload.health` predicate evaluated in the executor. That covers under-execution: a job whose downstream artifact is rotting. It does not cover over-execution, and measurement shows over-execution is the more expensive failure. One agent-created schedule on a `*/10` cron, whose goal was to drive three pull requests to merge, kept firing for five days after all three had merged: **866 runs, 831 of them (96.0%) reporting the work already done**, roughly 144 per day. Its own prompt already instructed it to "be idempotent: check state before acting". It complied on every run and the waste happened anyway, because it had no way to record that it was finished and no way to act on knowing it.

A second class of waste compounds it. Turn-budget exhaustion is **150 of 213 recent failures (70%)**, and it is misclassified twice over. It surfaces as `reason: "worker_failed"`, which is in `RETRYABLE_WORKER_ERROR_REASONS`, so a deterministic failure is retried up to three times with an identical budget that cannot succeed, and the partial work is discarded because the failure branch of `recordRunEnd` passes no `outputText`. The doctor's only auto-remedy, a `max_turns` patch, is gated on `/max(?:imum)?\s*turns|max_turns/i`, but the runtime's actual wording is `Reached maximum number of turns (N)`; the regex requires `maximum` followed by optional whitespace then `turns`, so it never matches. Measured: a 14-day substring census returns zero rows for `max_turns`, `turn limit`, and `turn_limit` while 150 runs died of a turn cap. Every such job therefore takes the generic branch, which patches `max_turns: 15`; because the payload merge is a one-level spread (`{...currentPayload, ...patch}`, despite being named `deepMergePayload`), that scalar replaces the current value outright and *downgrades* any job configured higher. Note the failure reaches the worker by two different routes depending on how the SDK terminates: a thrown stream error carrying that message (the observed majority), and a terminal `SDKResultError { subtype: 'error_max_turns' }` frame that `bounded-query.ts` drops because it accumulates only on `subtype:"success"`. Both must be classified, and neither may be detected by matching prose in a message.

The symmetric fix was designed and rejected: a declarative `payload.intent` block carrying a satisfaction predicate plus a stand-down policy, evaluated before dispatch. Three findings killed it. The motivating job cannot declare such a block, because `schedule_create` writes a fixed payload and exposes no parameter for one, so every agent-created schedule is unreachable by the mechanism. The registry cannot express the condition, because `extractHealthPayload` holds exactly one predicate string with no combinators, and none of the three registered predicates reads git or authenticated HTTP state; ADR 0001 recorded this same limit when it rejected a declarative reconciler engine. And a pre-dispatch gate in the producer would violate ADR 0001's constraint that predicate I/O stay out of the tick loop, since the producer holds a single permit across the tick, while moving it after `claimAndStartRun` means a "skipped" run must close a committed row with a terminal status that no existing status consumer recognises. Alternatives also considered: (a) driving adoption of the existing `payload.health` predicate, rejected because it measures artifact freshness rather than goal achievement and its alert rail dedupes against the most recent note of a shared kind, so two jobs in a non-fresh state alternate and never suppress; (b) standing a satisfied job down via `enabled=false`, rejected because `schedule_cancel` deletes the row and no enable path exists in any tool or CLI, making a false positive silent and unbounded in time.

Zero adopters of the Phase 2 predicate is the load-bearing evidence. It is not adoption lag. It indicates that job-creation time is not where the knowledge lives. The agent already reaches the correct conclusion on every run; it has no channel to persist that conclusion or act on it.

## Decision

1. Intent satisfaction is an in-band signal produced by the run, not a predicate declared in JSON. A run that determines its goal is met reports that through a per-run tool bound to its own job id, through the existing `JobRunToolsProvider.forRun` seam, guarded the same way `schedule_cancel` is guarded. No new payload schema, no second predicate registry, and no new `job_runs` terminal status.
2. Budget exhaustion is a distinct, deterministic failure reason. Both termination routes are classified into one `budget_exhausted` `WorkerError.reason`: the terminal error frame, by surfacing the SDK's subtype out of `bounded-query.ts` instead of collapsing it to `empty`; and the thrown stream error, by recognising the runtime's exhaustion message where an opaque cause becomes a typed `WorkerError`. The classifier lives beside the reason union in core and is applied at every such boundary — the prompt worker, the workflow worker, and `define-worker`'s catch-all, which is the one the brokered reasoner lanes (dream, wake, bulletin) fail through. Classifying only the worker paths would have left those lanes retrying an identical budget three times. The classifier is kept deliberately narrow: it must not match the SDK's own `maxTurns` option name, or an error merely echoing the request options would be misread as a ceiling and silently lose its retry. The reason is excluded from `RETRYABLE_WORKER_ERROR_REASONS` because retrying with an identical budget cannot succeed, and still counts toward `failStreak` so the doctor's existing payload-patch rail remains the budget-raising path. Downstream consumers key on the **reason**, never on prose in a message; the current regex-on-message remedy is the defect this replaces. No patch may lower an existing `max_turns`.
3. A finite goal must be expressible as a finite schedule. `schedule_create` gains a bounded form so that "do this until it is done" stops being encoded as an infinite cron. Standing a job down never flips `enabled` from an automated signal; that authority stays with an explicit actor, matching the authority `schedule_cancel` already grants.

## Consequences

Easier: a deterministic failure stops consuming three budgets instead of one; turn exhaustion becomes countable and distinguishable from an SDK crash; the doctor's only auto-remedy becomes reachable for the case it was written for; a finished job can say so with the knowledge it already has. Harder: `WorkerError.reason` is a typed union, so a new member touches the worker registry and both workers, and the reason must be threaded through `bounded-query`'s outcome type rather than collapsed to `empty`. Deferred deliberately: prior-run injection into the prompt (the cheapest way to convert re-derivation into verification) and the `job_stand_down` tool itself are specified here but ship separately, smallest first. Risk: a stand-down tool is an irreversible-feeling action from the operator's seat, which is why it is scoped to agent-created rows and why the re-enable gap is recorded as a prerequisite rather than assumed away. This ADR does not revisit ADR 0001; Phase 2 remains correct for the problem it addresses.
