🌙 Luna — System Architecture

A modular, local-first AI agent framework built on Effect-TS and Bun. A cloud Claude model is the substrate; Luna owns the runtime, persistent memory, tools, multi-account brokering, and a nightly self-alignment loop — reachable from a CLI, a web UI, and a floating desktop widget over your own private network.

1What Luna Is

Luna is not a chatbot wrapper. It is an agent framework: a composition of Effect-TS service layers — account brokering, a session store, plug-and-play memory, telemetry, a chat surface, and MCP tool servers — that runs on your own machine and drives a Claude model as its reasoning substrate.

🏠 Local-first

All durable state lives in ~/.luna/. SQLite is the system of record. Nothing leaves the box unless a tool call explicitly sends it.

⚡ Bun-native

The runtime is Bun, not Node. bun:sqlite is the driver; the Vectorlite HNSW extension is loaded at process boot for semantic memory.

🧩 Modular (Effect v3)

Every capability is an Effect.Service Layer with a typed interface, composed into a single ManagedRuntime at the server boundary.

🔑 Multi-account

An AccountBroker routes queries across Anthropic accounts by label, with secrets resolved from 1Password / env / file at acquire-time.

🧠 Persistent memory

Hybrid BM25 + vector (HNSW) recall over SQLite. The agent searches before answering and saves durable facts as it learns them.

🌗 Self-aligning

A nightly Dream proposes beliefs about the operator; a survey confirms them; confirmed beliefs inject into every new conversation.

Identity. Luna presents as "Luna," not Claude. DNA.md — Luna's self-description — is loaded into the system prompt of every thread. The Claude model is "the substrate, not the identity: a human is not their neurons; Luna is not its weights."

3System Map

Three planes: clients speak one WebSocket protocol to the chat server, a single Effect runtime that brokers a Claude subprocess and reads/writes four local stores. Ollama (local) serves embeddings; Claude (cloud) serves reasoning.

5Chat Runtime & the Turn Lifecycle

A "thread" is a long-lived Effect scope. When created, ChatService wires a prompt Queue into SDKAdapter.query(), which holds a streaming connection to a Claude subprocess for the life of the thread. A user message is just an offer to that queue; the assistant's reply streams back through a producer/consumer pipe and fans out to every subscribed client.

Key mechanics

  • Per-thread streaming connection. The adapter converts the inbox Queue to an AsyncIterable and runs the SDK's for await loop as a detached producer feeding an unbounded queue; the consumer is an Effect Stream. Idle-timeout is disabled for chat threads.
  • Persist-then-offer. The user turn is written to SessionStore before it reaches the model, and every SDK message is mirrored to the store as it streams — so reconnecting clients get an accurate snapshot.
  • Message dispatch. stream_event → assistant-delta (cumulative text); assistant → assistant-done + tool-call frames; user → tool-result; result → cost + session-end observability events.
  • Scoped recall & post-turn capture. When enabled, a per-thread recallMemory hook injects bounded scoped recall as a system-prompt suffix before the finite resumed SDK query, and on the exactly-once result event an observeTurn hook runs in a supervised background fiber to extract inert durable-memory / belief-evidence candidates - never blocking the turn and never materializing an active belief. Turn extraction defaults on and is disabled with LUNA_MEMORY_TURN_EXTRACTION=0.
  • Bottom-up layer order. LunaSqliteBootstrap is provided last so it builds first — swapping in the Vectorlite-capable SQLite before any new Database() opens.

6The LLM, Accounts & Credentials

Luna never spawns the model directly. The @anthropic-ai/claude-agent-sdk owns the subprocess; Luna supplies the executable path and the credential overlay.

How claude is invoked

  • SDKClient calls the SDK's query(), which spawns the binary at LUNA_CLAUDE_CODE_EXECUTABLE (default: claude on PATH) lazily on the first stream pull.
  • The subprocess path matters operationally: a launchd/systemd service runs with a minimal PATH, so the installers persist an absolute executable path into ~/.luna/.env.

The AccountBroker

Hydrated from the accounts table at boot. Each acquireSession() picks an account and registers a finalizer that decrements its in-flight count when the query scope closes.

  • Implemented Load-balanced rotation — lowest in-flight, then least-recently-used.
  • Implemented Sticky-pin — chat threads bind to one account so the SDK's conversation cache stays warm across turns.
  • Aspirational Cooldown on rate-limit (429) — the filtering machinery exists, but no production path calls report({kind:"rate_limit"}), and cooldowns are in-memory only (lost on restart). Today a 429 keeps re-picking the same account.

The memory abstraction

MemoryRouter maps a namespace pattern to a backend. In production there is exactly one rule — { "*" → SqliteVectorBackend } — so all memory lands in memory.db. Writes route by namespace; reads-by-id fall through all backends; vector search dispatches to vector-capable backends.

Embeddings & hybrid search

  • Embedder. LUNA_EMBEDDER=ollama → real Ollama (model embeddinggemma, http://127.0.0.1:11434, vectors L2-normalized). Any other value → a deterministic FNV stub (dim 64) used in tests/offline. Note a typo in the env var silently falls back to the stub.
  • HNSW. The Vectorlite extension is bootstrapped once per process; the index is backfilled on connection open and persisted to a sidecar. If the extension can't load, it degrades gracefully to naive in-process cosine.
  • Hybrid recall. memory_search runs both vector KNN and FTS5 BM25, then fuses with Reciprocal Rank Fusion (RRF).
  • Two injection paths. Memory is reached through MCP tools - the agent can call memory_search itself, guided by a system-prompt addendum - and through automatic scoped recall: before each turn ChatService runs one bounded hybrid retrieval and appends a clearly delimited, untrusted <memory_context> block as a per-turn system-prompt suffix (replaced each turn, never written to the SDK transcript). Auto-recall is scoped to the operator (luna observing operator), defaults on, and is disabled with LUNA_MEMORY_AUTO_RECALL=0; it is bounded by LUNA_CHAT_RECALL_TIMEOUT_MS (default 2.5s, 0 disables the bound) and degrades to no injected context on timeout or search failure.

8Tools, Scheduler & Shell

The agent has 12 callable tools across four MCP servers, all auto-loaded onto every thread. @luna/tools is the builder/policy layer, not a tool source.

🧠 Memory mcp__memory__*

memory_save · memory_search · memory_delete

⏰ Scheduler mcp__scheduler__*

schedule_create · schedule_list · schedule_cancel

💻 Local shell mcp__local_shell__*

local_shell_run — execute in the attached terminal, with approval

🔭 Observability mcp__observability__*

obs_note · obs_notes_recent · obs_session_explain · obs_session_anomalies · obs_sessions_search

Scheduler

Implemented Cron schedules (5-field, parsed by effect/Cron) are persisted as rows in the jobs table; a single supervised JobTicker polls the table every minute, claims due rows, and dispatches each through a WorkerRegistry keyed by job kind (prompt / workflow / dream / wake). Every fire writes a job_runs row (per-fire audit), and schedules survive restart since the table is the source of truth. Not yet file-watch triggers are reserved but not implemented. (The legacy in-memory TriggerAgent + JobScheduler fiber-per-cron path was removed once the ticker became the only scheduler.)

Local shell

The agent doesn't run shell commands itself. local_shell_run sends a request over a WebSocket bridge to the attached luna terminal client, which prompts the operator for approval (default) or auto-approves inside a trusted container session. Results stream back. A bound thread owns the shell slot for its lifetime.

9Observability & Telemetry

One source, two sinks. ObservabilityService is an in-memory PubSub; every component emits structured ObsEvents (SessionStart/End, ToolCall, CostAccrued, AccountSwitch, RetrievalCall, Error, …) fire-and-forget — observability must never crash the host.

  • Sink 1 — events.jsonl: a background daemon appends each event as a JSON line (raw audit trail).
  • Sink 2 — analytics.duckdb: EventSink normalizes each event into a flat events row; SessionSync projects session lifecycle into a sessions table. The agent introspects these via the obs_* tools — the substrate for self-improvement.
Deferred: OTLP / OpenTelemetry export is aspirational, gated on a v3-compatible @effect/opentelemetry release. Telemetry today is local-only.

10The Alignment Loop

Luna's distinguishing capability: a closed loop that learns durable beliefs about the operator and feeds them back into every conversation — with a human confirmation gate, calibrated cadence, and no restart required. Proven end-to-end by loop.e2e.test.ts.

Stage by stage

  1. Dream Implemented — a 3am cron (0 3 * * *) gathers sessions + operator memories since a watermark, asks the model (via the SDK) to emit a strict JSON array of ops, and materializes them. memory_dedup auto-applies; belief_candidate is staged as proposed (inert). Partial staleness/contradiction ops are logged but never auto-applied.
  2. Survey Implemented — on WS connect, if due (by the EWMA cadence), the server pushes a survey-request: one mandatory task-quality Likert item plus up to three proposed beliefs. A keyboard-driven TUI modal collects verdicts. The issuedAt timestamp is the idempotency anchor for replay safety.
  3. Calibrate & activate Implemented — verdicts route through processVerdict with a log-first, idempotent write. Task-quality updates an EWMA with asymmetric smoothing (slow to trust, fast to claw back) that sets the next survey cadence (1–30 days). confirmed → activate (capped at 20, weakest evicted); rejected → retire; corrected → stays proposed. Gap correction text is not fed back to Dream.
  4. Inject Implemented — a background fiber refreshes the active-belief set every 30 seconds and composes a "What I believe about Operator" section ranked by confidence × recency × validation history. Each new thread reads it at creation — so a freshly-confirmed belief lands in the next conversation, no restart.
Why this is safe. Beliefs only influence behavior after a human confirms them; EWMA is conservative (slow up, fast down); every signal write is idempotent on issuedAt; and the EWMA explicitly excludes belief-validation signals to keep cadence and belief-trust as separate axes.

11Client Surfaces

Three clients, one protocol. They differ in framework and ergonomics, not in how they talk to the server. The Moon widget is the native desktop surface going forward — the standalone full-window Tauri shell (ui-tauri) was retired in its favor, so there is one Tauri app, not two.

⌨️ luna CLI Implemented

The operator's command surface (citty). chat (Ink TUI, readline fallback), account add/list/rm, memory status/reembed, doctor (4-layer preflight), pair (write configs + verify). Also hosts the local-shell bridge endpoint.

🌙 Moon widget Implemented Primary desktop UI

Luna's native desktop client: a 140×140 transparent, always-on-top crescent (Tauri 2) that expands to a chat panel. A single dependency-free HTML file — no build step. Global shortcut ⌘/Ctrl+Shift+K (self-healing chain). Connection stored at ~/.luna/moon-connection.json (0600); token kept out of localStorage. A 90s turn watchdog prevents endless spinners.

🖥️ ui-web Implemented

The full Solid.js web UI on Vite :5174. Chat + observability panes, an account switcher, the setup-mode terminal (xterm.js), and the alignment survey modal. Config in localStorage; auto-connects when a ≥16-char token is present.

Shared core. @luna/ui-shared supplies the transport + pure reducer; @luna/ui-shared-solid supplies the components. Caveat: the browser-safe wire.ts mirror omits several newer frames (local-shell, tool-call/result, memory-search, survey), so Solid clients see a narrower union than the server defines.

12The WebSocket Protocol (v2)

A single tagged-union protocol over one WebSocket per connection. UI_WS_PROTOCOL_VERSION = 2. The first frame is always hello, carrying the version + capability flags.

Authentication & readiness

  • Token, two forms: Authorization: Bearer <token> (Node/CLI) or ?token=… query (browsers, which can't set headers). Compared in constant time; the server refuses to start with a token under 16 chars (fail-closed).
  • Unauthenticated probes: GET /healthz → 200 "ok" (liveness); GET /readyz → JSON {status, mode, credentialOk} (distinguishes setup vs normal mode).
  • Rejections: bad token on upgrade → HTTP 401 + socket destroy; wrong path → 404; non-upgrade GET to the WS path → 426.
  • Version skew: the Moon client compares the hello version to a hardcoded expectation and shows an amber warning on mismatch — but never blocks the connection.

Server → Client frames

hello, event, drop, ping, bye, thread-list, thread-created, thread-snapshot, user-accepted, assistant-delta, assistant-done, assistant-error, artifacts-extracted, tool-call, tool-result, account-list, local-shell-request, local-shell-status, memory-search-result, memory-search-error, survey-request, pty-output

Client → Server frames

pong, bye, subscribe, unsubscribe, list-threads, new-thread, user-message, interrupt, local-shell-capability, local-shell-result, memory-search-request, survey-response, pty-input, pty-resize

Reconnect dedupe: thread-snapshot carries throughSeq, live frames carry seq; clients drop anything they've already seen.

13Boot Modes & Readiness

At boot, a credential gate decides which of two servers to build. This is why /healthz alone is insufficient to declare a deploy healthy — a credential-lapsed server still answers 200.

Setup modeNormal mode
TriggerNo accounts, or the claude-code:login account fails claude auth statusA usable credential is present
ServesA minimal layer + a claude setup-token pty over WS — operator logs in, then restartsThe full runtime: ChatService, broker, memory, scheduler, Dream/Survey
/readyz{mode:"setup", credentialOk:false}{mode:"normal", credentialOk:true}
The deepened readiness gate. /readyz derives its mode from the boot configuration. luna-update-server's rollback gate requires mode:"normal" (not merely a 200) — so a deploy that boots into setup-mode is rejected and rolled back, rather than silently accepted. Older servers without /readyz fall back to liveness-only for compatibility.

14Deployment Topology

The intended deployment: a Mac runs the clients, a separate Linux box runs the server, and they meet over a Tailscale tailnet. Two profiles coexist on the server: a bare-host stable (master) and an Incus-contained dev.

  • stable / master — a standard systemd system unit (luna-chat-server.service), repo at /root/luna/stable/repo, on :4753. The unit explicitly sets HOME/PATH (a root systemd service gets neither by default on modern systemd).
  • dev — an Incus container reached through a host proxy; the in-container server binds loopback and exposure is controlled at the host-proxy layer.
  • Bind posture — the installers auto-resolve the bind to the host's Tailscale IP when a tailnet is present (so remote clients reach it), else loopback; a public 0.0.0.0 bind requires an explicit, warned opt-in.

15Security Model

🔒 Transport = Tailscale

The WebSocket layer is plaintext ws:// with the token in the URL — it has no transport confidentiality on its own and is meant to run behind a Tailscale tailnet. luna doctor warns when a client points at a non-tailnet, non-loopback host.

🎟️ One auth layer

A bearer token (≥16 chars, constant-time compared) is the only auth. The server fails closed if it's unset. Token rotation is a re-pair away.

🗝️ Server-side credentials

The Claude OAuth credential lives only on the server (CLAUDE_CONFIG_DIR, dir 0700). Clients never read or write it. Account secrets resolve from 1Password/env/file at acquire-time and are Redacted in memory — never logged.

📁 Secrets at 0600

~/.luna/.env and moon-connection.json are created mode 0600 from birth; the HNSW sidecar is re-tightened to 0600 after every close.

Honest caveats. Plaintext ws:// + token-in-URL is only safe inside a private network. A public 0.0.0.0 bind is a loud, deliberate opt-in. The local-shell tool can run arbitrary commands on the client host — gated by per-request approval, but powerful by design.

17CI & Verification

CI (.github/workflows/ci.yml) runs on every push/PR with two hard gates and two documented known-red baselines.

✅ Hard gates (block merge)

Frozen lockfile — bun install --frozen-lockfile catches lockfile drift.
Secret scan — fails on bare 40+ hex tokens, real sk-ant- keys, or access/refresh-token literals in tracked files.

⚠️ Known-red baselines (surfaced, non-blocking)

typecheck — a documented pre-existing tsc baseline.
test — the full suite has known env failures (bun:sqlite/jsdom). Run for visibility, ratcheted to green over time.

Beyond CI, the deploy-risk gate is the set of boot smokes — real-layer ManagedRuntime builds for setup and normal mode — because chat-server.ts has no tsc gate of its own. The smokes prove the layer graph actually assembles before any deploy.
