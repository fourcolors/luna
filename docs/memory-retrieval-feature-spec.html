Current Database Contract

/root/.luna/memory.db

Canonical Record Store

memory_keyed owns the durable memory record. This table is the safe migration source because it keeps namespace, kind, opaque JSON content, schema version, timestamps, and tags. The nullable scope_json / provenance_json columns carry portable MemoryScope / MemoryProvenance metadata (added by the scoped-memory pipeline via an idempotent open-time ALTER TABLE ... ADD COLUMN guard); legacy rows leave both NULL. 

CREATE TABLE memory_keyed (
  id TEXT PRIMARY KEY,
  namespace TEXT NOT NULL,
  kind TEXT NOT NULL,
  content_json TEXT NOT NULL,
  schema_version INTEGER NOT NULL,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  tags_json TEXT NOT NULL,
  scope_json TEXT,
  provenance_json TEXT
);

Searchable Vector Store

memory_vectors is one-to-one with memory_keyed. It stores the vector blob and the plain text mirrored into FTS5. Today it does not record which embedding model, prompt format, or source hash produced the vector. 

CREATE TABLE memory_vectors (
  id TEXT PRIMARY KEY REFERENCES memory_keyed(id) ON DELETE CASCADE,
  namespace TEXT NOT NULL,
  embedding BLOB NOT NULL,
  dimension INTEGER NOT NULL,
  text TEXT NOT NULL,
  ts INTEGER NOT NULL
);

Keyword Index

memory_fts indexes memory_vectors.text with FTS5. Insert, update, and delete triggers keep the keyword index synchronized with vector rows. 

CREATE VIRTUAL TABLE memory_fts
  USING fts5(
    text,
    content='memory_vectors',
    content_rowid='rowid',
    tokenize='porter unicode61'
  );

Approximate Vector Index

memory_vectors_hnsw is a Vectorlite virtual table. On the deployed dev DB it was created as float32[768], matching embeddinggemma. 

CREATE VIRTUAL TABLE memory_vectors_hnsw
  USING vectorlite(
    embedding float32[768],
    hnsw(max_elements=100000)
  );

Target Retrieval Flow

atomic memory first, document chunks later

1. Save Agent calls memory_save; Luna writes the canonical record to memory_keyed.
2. Format Luna builds a model-aware embedding input from namespace, kind, tags, and text.
3. Embed Ollama returns a normalized embeddinggemma vector. Metadata records the model and format.
4. Index memory_vectors updates; triggers sync FTS5 and HNSW indexes.
5. Search Query formatting, vector search, BM25, RRF fusion, then optional reranking.

F1. Embedding Metadata Columns

Add enough metadata to know whether an existing vector is compatible with the currently configured embedder and embedding prompt format.

Field Purpose Default for existing rows
embedding_provider Distinguishes stub, ollama, or future providers. unknown
embedding_model Records embeddinggemma, qwen3-embedding:0.6b, etc. unknown
embedding_format Versioned formatter name, for example raw-v0 or memory-note-v1. raw-v0
embedding_input_hash Hash of the exact formatted input sent to the embedder. empty string
embedded_at Timestamp for status and stale-vector audits. 0

Acceptance criteria: old DBs open without manual work, new saves populate all metadata, and search ignores or reports incompatible rows instead of silently mixing vector spaces.

P0 operator CLI luna-server Done

F2. Memory Status + Re-embed Command

Build an operator command that audits the memory DB, reports incompatible rows, and re-embeds records from memory_keyed. This is required before judging retrieval quality, because the live dev DB currently has 64d vectors while the active index is 768d. 

luna memory status
luna memory reembed --dry-run
luna memory reembed --namespace notes
luna memory reembed --force --limit 100
  • Status reports row counts grouped by dimension, provider, model, and format.
  • Dry run prints which rows would be rebuilt and why.
  • Re-embed recomputes the formatter output from memory_keyed.content_json, not from stale vector text alone.
  • Each row is updated transactionally so FTS5 and HNSW triggers stay in sync.
  • The command exits non-zero if the active HNSW dimension does not match the configured embedder.
P1 retrieval quality prompt formatting Done

F3. Query and Document Embedding Formatting

Move raw text embedding behind two explicit formatters: one for saved memory records and one for search queries. 

// Query
task: search result | query: {query}

// Memory record
title: {namespace}/{kind} tags:{tags} | text: {content.text}

The raw memory text should remain in memory_vectors.text for BM25 and tool output. Only the vector input changes. This keeps keyword search honest while making semantic search more model-friendly.

Deterministic test corpus that exercises the actual MemoryRouter path. Two tiers: Tier 1 mechanics (stub embedder, vitest) and Tier 2 paraphrase recall (real Ollama, standalone bench). Plus RetrievalCallEvent for per-search telemetry.

  • Done: seeded project (10), user-preference (10), and distractor (10) facts in packages/memory/bench/corpus.json with 60 paraphrase queries total.
  • Done: Tier 2 bench asserts hybrid search returns the correct id at rank ≤ 5 for natural paraphrases — packages/memory/bench/paraphrase-recall.ts. Exits non-zero if overall recall@5 < 0.9 (override via LUNA_BENCH_RECALL_THRESHOLD).
  • Done: Tier 1 mechanics suite covers topK enforcement, namespace isolation, idempotency, empty-corpus, hybrid ranking, and RetrievalCallEvent telemetry — packages/memory/test/retrieval-mechanics.test.ts (6 cases).
  • Done: per-search observability via RetrievalCallEvent (queryDigest, embedder provenance, candidateCount, topScore, durationMs, status) — wired at MemoryRouter level so every consumer gets identical telemetry.
  • Done: stale rows detected by memory status — sqlite-vector-maintenance.test.ts:123.
  • Done: re-embed upgrades rows to the configured dimension and metadata — sqlite-vector-maintenance.test.ts:164, memory-cli.test.ts:215.
  • Done: corpus contains no personal data (work email only, no credentials or private facts).

Canonical baseline run (2026-05-25): Ollama + embeddinggemma:latest (307M, 768-d) inside the luna-dev container against the host's Ollama daemon. 60 paraphrase queries. Overall recall@5 = 0.950 (preference 1.000, project 0.900); recall@1 = 0.800; MRR = 0.863. Comfortably above the 0.9 go/no-go gate on top-5, and strong on top-1 too — F5 reranker is not justified. The only failures left are 3 project-kind queries with terse technical vocab; worth a future per-query dive but not a reranker trigger. Local cross-check with nomic-embed-text (768-d) gave 0.917 / 0.417 / 0.605 — same overall verdict, much weaker top-1.

P2 ranking optional model Not started

F5. Optional Reranking Stage

After hybrid search returns the top 20-50 candidates, allow an optional local reranker to reorder candidates before tool results are returned.

  • Default off on the old T2 Mac unless performance is acceptable.
  • Provider controlled by env, similar to the embedder.
  • Search still works if the reranker is unavailable.
  • Log ranking inputs and outputs to observability, not to memory.db.

Gated on F4 bench data. Only build if the real-Ollama recall@5 falls below 0.9, and with a specific per-kind target informed by the per-kind breakdown. Don't build a fix for a non-problem.

P2 documents new tables Not started

F6. Chunked Document Memory

The current memory_vectors.id PRIMARY KEY shape is correct for atomic memories but cannot store multiple chunks for one source document. Add chunk tables only when Luna starts indexing longer docs, transcripts, or project files.

Deferred — no document ingestion use case yet. Atomic memory is what the chat agent uses today. Adding a schema + tool surface for documents before there's a caller would be premature scope.

Migration Sequence

lowest risk first

  1. Done. Add metadata columns to memory_vectors with safe defaults.
  2. Done. Expose embedder identity from EmbedderService so saves and status can compare provider, model, dimension, and format.
  3. Done. Add formatter helpers and route both put() and search() through them.
  4. Done. Add luna memory status and luna memory reembed --dry-run.
  5. Pending. Run re-embed on luna-dev; confirm all rows become 768d and metadata is populated. (Tooling exists, deploy/run still needed — live snapshot still shows 64d rows.)
  6. Done. Regression tests around the migration and retrieval path — mechanics + paraphrase corpus shipped (see F4).
  7. Pending. Only then consider reranking and chunked document memory.

Do not skip re-embedding.

A 64d vector from the stub embedder and a 768d vector from embeddinggemma are different spaces. Mixing them makes retrieval look broken even if the current code is correct.

Keep FTS text raw.

Format the string passed to the embedder, not the text stored for BM25. That preserves exact keyword behavior and avoids returning formatting noise to the agent.

Luna uses Vectorlite's HNSW table for fast approximate nearest-neighbor search when the SQLite extension loads successfully.
