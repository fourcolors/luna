## Summary
This PR reworks Moon's self-update from a synchronous "check + abrupt download_and_install + restart" into a **staged, user-paced experience**: quiet background discovery (8s boot + 6h poll), live-progress download+verify, bytes held in `UpdateManager`, and explicit "Restart to update" that first persists layout + a `pending-update.json` reopen marker for the chat window before `update.install(bytes)` + `app.restart()`. Three surfaces stay in sync via `update://*` event stream + `update_state` replay: full narrative panel (settings-updates.js), composer banner (chat.html), and orb pip (index.html + widget-registry size bump). 10 files, +2010/-104.

Correctness impression: **Strong**. The Rust state machine, single-flight guard (phase check under short Mutex critical section), staged bytes handoff (take before any side effects), layout-before-relaunch ordering, per-version dismissal, safe textContent DOM, event completeness (checking/available/progress/verifying/ready/error/none), and replay are all correctly implemented and defended in comments. Cargo check clean; 61 Rust tests (incl. new UpdateInner DTO projections) + 638 vitest (new panel-updates, update-banner, update-pip + panel-window mods + snapshot) pass per PR metadata. No obvious races in the staged path, no raw `.unwrap()` on locks in update code (all use `unwrap_or_else(|e| e.into_inner())` poison recovery), no innerHTML on remote notes, color-mix + tokens only, ARIA roles present.

Dominant risk areas: (1) UI visual changes shipped without the required rendered screenshots (see Project Alignment); (2) ~28 MiB `Vec<u8>` held in managed state until apply (documented gotcha, memory residency if user defers restart); (3) restart fidelity depends on write_panel_layout + pending-update marker + pre-existing thread snapshot path (all best-effort, HOME-dependent in places); (4) jsdom coverage is excellent for logic but per CLAUDE.md cannot substitute pixel/layout proof for the banner/pip/panel chrome/animations.

### Issue 2 -- Severity: nit
- File: apps/ui-moon-tauri/src-tauri/src/main.rs:1395 (inside write_panel_layout)
- Description: `let _ = std::fs::write( &path, serde_json::to_string_pretty(&doc).unwrap_or_default() );` The `unwrap_or_default()` on serialization (for this tiny controlled struct it cannot fail in practice) will silently write an empty or default string to `~/.luna/layout.json` on any future serde surprise. The call is best-effort and only at apply time (plus other paths), but an empty file on disk is a worse outcome than leaving the prior layout.
- Suggestion: Change to `.unwrap_or_else(|_| String::from("{\"version\":1,\"panels\":[]}"))` or just `serde_json::to_string(&doc).unwrap_or_default()` (compact is also fine for this file) and keep the outer `_ =`. Consider adding a one-line eprintln on the rare serialize path for operator visibility.
- Status: open

### Issue 3 -- Severity: suggestion (resource / UX)
- File: apps/ui-moon-tauri/src-tauri/src/main.rs:76 (`staged: Option<(tauri_plugin_updater::Update, Vec<u8>)>` in UpdateInner), 240 (stage site), 326 (take in apply_update), 349 (install)
- Description: Once downloaded+verified, the full ~28 MiB archive bytes live in the `UpdateManager` managed state (behind the Mutex) until `apply_update` explicitly takes them or the process exits. The background loop (3293) and `start_update_download` can overwrite a ready staged build with a newer one (gate only blocks checking/downloading phases, not ready), but a user who stages and then never restarts keeps the bytes resident for the lifetime of the Moon process. PR "Gotchas" notes it ("Verified bytes are held in memory until you apply — nothing restarts on its own"), but no upper bound, explicit "forget staged" path, or size accounting is present.
- Suggestion: Add a short comment at the staged field and in the background task noting the residency cost. If future requirements demand it, a `clear_staged` command or "ignore this version" that drops the Option without changing phase could be added; for the current "staged + user-triggered" contract this is acceptable.
- Status: open

### Issue 4 -- Severity: nit (defensive / future-proofing)
- File: apps/ui-moon-tauri/frontend/chat.html:5432 (`_anchor`), 5454 (guard), 5508 (insertBefore); analogous insertion assumptions in panel and pip wiring
- Description: `UpdateBanner._anchor()` falls back to bare `.composer-input-wrap` or returns null; on null the onReady silently returns with no banner and no log. The pip and panel are more robustly mounted in their host HTML. If the chat input DOM is refactored (class rename, structure change), the in-chat surface will silently degrade while the other two surfaces still work.
