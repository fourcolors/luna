1Where we are, what's missing

The React app already anticipates a native swap, and the wire already carries every notification-worthy event. What's missing is the native layer plus reconnect resilience.

ui-web today

Luna Studio (React SPA)

React 18 + Vite, single typed-frame WS, token-is-session auth. transport.ts:9-12 already anticipates a Tauri swap behind the Transport interface. Real iframe/CSP widget sandbox. But: no reconnect, no Notification API, no unread state - reducer.ts:508,560 no-op every notification-worthy frame.

native precedent

Moon (Tauri v2)

Proven Tauri v2 shell: notify command + least-privilege capability, staged updater, release pipeline, WKWebView cache-purge fix. Working background-delivery notification with focus/dedupe/opt-out gates. But: no tray, autostart, deep-link, single-instance, or badge anywhere.

already wired

The wire carries everything

assistant-done + delivery marker = turn done. suggested-action-set = chips. job-input-request (broadcast) + secret-request (targeted) = 'Luna needs input'. seq/throughSeq dedupe makes reconnect-resume idempotent.

2The shell decision

Both independent design variants and the judge converged on a new sibling Tauri app. The costs are what decide it, so they are shown, not summarized away.

Recommended

New sibling Tauri app

com.luna.studio embeds ui-web's Vite dist as tauri:// assets. Copies Moon's proven infra with identifier/tag/stamp changes. ui-web renders with zero code changes; native calls no-op in a browser tab.
Cost: a second release train (own keypair, bump-studio, release-studio.yml) + ~50 lines of cache-purge FFI duplicated.

Rejected

Studio window inside Moon

One binary, one updater - but Moon has no bundler (hand-authored HTML dist). A React SPA there means bolting Vite onto an app that avoids one.
Cost: release coupling - a Studio-only fix forces a full orb re-sign; a red ui-web build blocks orb releases.

Rejected as driver

PWA / browser tab

A same-day win for an always-open tab, and that is all. Kept as the graceful-degradation path inside the same code (web Notification API + title badge), not a separate phase.
Stopping here: no closed-window notifications, no dock badge, no launch-at-login, no OS deep links, no signed auto-update.

3Notification architecture

Server event to existing WS frame to useStudioNotifier (new) to Moon-ported gates to a thin Rust command to Notification Center. No new wire protocol.

The path, end to end.

Three server sources - chat-service.deliverResult (stamps luna_delivery), the suggested-actions service, and request_input/request_secret - all land on one WebSocket (the ServerFrame union). useLunaData.onServerFrame (which the reducer no-ops today) branches two ways:

notify path

useStudioNotifier (new)

Gates: focused? deduped? opted out? On isTauri it calls Rust notify_thread(kind, title, body, threadId) to macOS Notification Center; in a browser tab it falls back to the web Notification API.

badge path

useUnreadBadge (new)

Persisted per-thread last-seen watermark, calls setBadgeCount() - built in since Tauri 2.2, and the workspace is on 2.11.2.

On macOS a banner click activates the app only (no per-banner payload), so a focus-regain handler routes to the pending attention thread or shows an attention strip.

4What cross-checking corrected

Four places where one research stream was wrong and another caught it - each changes the plan materially.

Corrections.
✓ corrected

Dock badge is free

The judge specced custom objc2 dock-tile FFI. Wrong: setBadgeCount() shipped in Tauri 2.2.0 and the workspace resolves 2.11.2. Phase 3 got simpler.

✓ corrected

Plain ws:// works from the Tauri origin

Web research warned of mixed-content blocking. Moon's shipped CSP (connect-src 'self' ws: wss:) talks plain ws:// in production. No TLS termination requirement.

✓ corrected

'Needs input' is wirable now

JobRunStatus includes waiting (jobs-store-types.ts:77) and job-input-request broadcasts to every client. The doc claiming otherwise (widget-system.md:814-817) is stale - worth a one-line fix.

✗ corrected

Banner click-to-thread does NOT work on macOS

The judge's Phase 2 gate assumed it. The plugin's Actions API is mobile-only (open upstream since 2021). A banner click still just activates the app - so Phase 2 routes on focus-regain, and true per-banner routing (objc2 + UNUserNotificationCenterDelegate) becomes optional Phase 5.

5Phases & proof gates

Each phase ends at a gate this repo's rules demand: rendered screenshots for UI, real Notification Center banners for OS work - never just green tests.

The ladder.
Phase 0 · 1 session

Shell spike - de-risk WKWebView first

Scaffold apps/ui-studio-tauri; embed ui-web dist (frontendDist: ../../ui-web/dist, devUrl :5174); port Moon's cache-purge verbatim with a .studio-webview-version stamp. No notification code allowed yet.

Gate - In the real WKWebView window: live thread streams, vibe-coded widget renders inside its sandbox (no __TAURI__ leak), clipboard works with capability declared. Screenshot proof.

Phase 1 · 1-2 sessions

Resilience spine - an always-connected window

Adopt the already-built LunaWsAdapter backoff transport (adoption, not a build - fixes web too) + app-level auto-pong. Token moves to OS keychain via load_token/save_token (preserve the VITE_UI_WS_TOKEN build guard, mirror in CI). luna://thread/<id> deep link + single-instance + last-thread restore.

Gate - Kill the server: backoff reconnect, transcript resumes with no duplicates. Cold-launch a luna://thread/<id> lands on that thread. Token verified in keychain.

Phase 2 · 1-2 sessions

Notifications - the headline

useStudioNotifier maps four categories: turn/job done (delivery marker distinguishes background from live; live replies deliberately not notified), suggested action, and needs input (job-input-request broadcast + secret-request targeted). Port Moon's gates, request permission on first run, fail soft. Rust notify_thread via per-command capability. Banner click focuses Studio; on focus regain it routes to the single pending attention thread (attention strip when several pend). Web fallback in a browser tab.

Gate - With the window backgrounded, capture a real Notification Center banner for EACH category; show focus suppression and no double-banner across Studio + Moon on the same thread.

Phase 3 · 1 session

Daily-driver shell

useUnreadBadge + setBadgeCount(); tauri-plugin-autostart; tray icon with unread tooltip and open/quit.

Gate - Badge shows an accurate count that survives relaunch; login-item relaunch works; tray works.

Phase 4 · 1-2 sessions

Distribution - own release train

Staged updater port (persist session before app.restart()), a new minisign keypair (never Moon's), bump-studio.ts + release-studio.yml (studio-v* tags), Latest-flag re-anchor scoped so the two apps never steal each other's updater feed.

Gate - Signed install, publish studio-v(x+1), full auto-update round trip with the WKWebView serving the NEW dist (cache stamp bumped).

Phase 5 · optional

True banner-click routing

objc2 + UNUserNotificationCenterDelegate threading threadId through userInfo, delivering real click-to-thread. Only testable in an installed .app. Decide after living with the Phase 2 focus-regain UX.

Gate - Real click-to-thread from a background banner in the installed app.

Cross-cutting (server, separate slice) - per-connection multi-registration for secret-request/local-shell. Today they are last-subscriber-wins per thread, so Studio auto-subscribing a thread Moon has open silently steals its interactive prompts. Benefits Moon too. Whether to build it now is Decision 1 below.

6Risks

Five real hazards, each with the containment that keeps it from becoming a bug.

Risk register.

WKWebView drift at React scale

Why it's real: srcdoc/CSP sandbox + clipboard proven only in Chromium; largest webview payload in the repo.

Containment: Phase 0 exists solely to expose this before feature work.

Prompt stealing between Studio and Moon

Why it's real: last-subscriber-wins secret/local-shell bridges.

Containment: Decision 1; until then, a v1 policy, not code hope.

Focus-regain routing is a heuristic

Why it's real: several simultaneous attention events are ambiguous.

Containment: In-app attention strip when >1 pending; Phase 5 if insufficient.

Two release trains

Why it's real: double CI/signing surface; shared latest.json namespace.

Containment: Strict identity separation: identifier, keypair, tag prefix, Latest re-anchor.

Public repo secret leak

Why it's real: VITE_UI_WS_TOKEN baked into a dist would ship the tailnet secret.

Containment: Existing build guard preserved + mirrored in release-studio.yml; token in keychain; config user-entered at runtime.

7Decisions I need from you

Five open decisions own the shape of the build. Recommended option is marked; comment on any of them and I fold your answers into the spec, delete the open questions, and start Phase 0.

Decision 1

Moon coexistence (blocks Phase 2 needs-input)

  • Recommended: Studio avoids auto-subscribing threads with pending prompts - a cheap client-side guard, ships now.
  • One client at a time - pure policy, zero code, relies on discipline.
  • Build per-connection multi-registration now - the real fix, benefits Moon, +1-2 sessions before Phase 2.
Decision 2

Badge semantics

  • Recommended: Unread threads - calm, matches the thread-list mental model.
  • Unread messages - busier, inflates fast on chatty threads.
  • Attention-only (needs-input + suggested) - badge = 'Luna is waiting on you'.
  • Also: does the tray mirror the badge?
Decision 3

Banner-click routing

  • Recommended: Focus-regain routing first, judge Phase 5 later - what mature Tauri chat apps ship.
  • Pull Phase 5 forward - true click-to-thread from day one, +1-2 sessions, installed-.app-only testing.
Decision 4

Long-term: Moon & Studio

  • Studio replaces Moon's chat; orb goes ambient - separation is a stepping stone.
  • Permanent siblings - Phase 4's separation is forever.
  • Decide after a month of daily-driving - defer, evidence over speculation.
Decision 5

First-run token provisioning

  • Recommended for v1: Manual paste into Settings - exists today, zero new surface.
  • luna://connect provisioning deep link - slick, but deep links only test in an installed .app.
