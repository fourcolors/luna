Input

stage 2

BM25 probe

SQLite FTS5 + Porter tokenizer
Top-20 from documents_fts. SHORT-CIRCUIT: if topScore ≥ 0.85 AND gap ≥ 0.15, skip stages 3–4 entirely → straight to rerank.
↓
stage 3 · custom

Query expansion

qmd-query-expansion-1.7B-q4_k_m.gguf
Tobilu's own fine-tuned 1.7B model. Generates 3 variants per query: • lex — keyword reformulation • vec — semantic paraphrase • hyde — hypothetical answer

stage 4

Embedder

embeddinggemma-300M-Q8_0 (768d)
Task prefixes: docs: "title: X | text: Y" query: "task: search_result | query: Z" Batch-embedded: original + vec + hyde in one call.
↓
stage 5

Vector index

sqlite-vec virtual table
vectors_vec (768d cosine, native C extension) 20 hits per query variant.
↓
stage 6 · custom

Fusion — Reciprocal Rank Fusion

Weighted RRF (k=60)
Merges all retrieval lists (BM25 + 3× vec). 2× weight on first BM25 list AND first vec list to prioritize the obvious match path.
↓
stage 7 · custom

Chunk-level reranker

qwen3-reranker-0.6b-q8_0
Picks best chunk per file (keyword + intent terms). Reranks ~40 chunks NOT full docs (token-cost trick). Cross-encoder scoring with intent prefix. Cached by query+chunk hash.
↓
stage 8

Output

Ranked chunks + scores + snippets
qmd://collection/path:line + score% + diff-context.

Gap in Luna vs QMD
Reading the diff: Luna today is QMD's stages 4 + 5 only (embed + vector lookup), with a stub embedder. Everything QMD does in stages 2, 3, 6, 7 — BM25, query expansion, RRF fusion, chunk reranking — is a gap. A fair head-to-head on retrieval quality would either (a) match embedders (Gemma both sides) and compare stage 4+5 only, or (b) build out Luna's missing stages first. Latency comparison is ~700× in Luna's favor today, but Luna is doing ~700× less work — three GGUF model calls vs one in-process cosine sweep.
